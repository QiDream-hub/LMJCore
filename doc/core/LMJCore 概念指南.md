# LMJCore 概念指南

_——用指针把嵌套数据“摊平”的高性能存储内核_

---

## 一、为什么需要 LMJCore？

现代应用常需处理高度动态、深度嵌套的数据（如 JSON、配置树、图结构）。传统数据库要么强制模式（如关系型），要么在读写性能上妥协（如文档数据库解析开销大）。

**LMJCore 的答案是**：

> **不提供查询，只专注极致高效的存储** —— 把复杂结构“拆开存”，用**全局指针**重新“拼起来”。

它不是完整数据库，而是一个**可嵌入的存储内核**，为上层查询引擎（如未来的 `LMJQuery`）提供坚实、快速、一致的数据基石。

---

## 二、核心思想：三句话讲清 LMJCore

1. **万物皆指针**  
    所有对象和集合都有一个 **17 字节的全局唯一 ID**（首字节标识类型：`0x01`=对象，`0x02`=集合）。这个指针就是它们在系统中的“身份证”。
    
2. **数据被彻底扁平化**  
    嵌套结构（如 `{user: {name: "Alice"}}`）不会以树形存储，而是被**拆成独立片段**，分散在两个物理空间中。
    
3. **靠两个“仓库”协作**
    - **`set`（集合区）**：回答“这个实体有哪些关联项？”（如对象的成员名列表、集合的元素列表）
    - **`main`（主存储区）**：回答“这个成员的具体值是多少？”（如 `name → "Alice"`）

通过指针 + 两个仓库，既能高效点查，又能灵活组合任意复杂结构。

---

## 三、存储模型：两个空间，一套规则

### ▶ 空间 1：`set` —— “集合区”

- **作用**：记录一个实体“拥有什么”。
- **特点**：
    - Key = 实体指针（17B）
    - Value = 成员名 或 集合元素（可多个，自动去重排序）
    - 对象用它存**成员名列表**；集合用它存**元素列表**
    - **不保留插入顺序**，按字典序自动排序

> ✨ 比喻：`set` 就像一个贴了标签的集合袋，你往里扔“name”、“age”这些纸条，袋子会自动整理好（但不会记住你扔的顺序）。

### ▶ 空间 2：`main` —— “主存储区”

- **作用**：存储具体值。
- **特点**：
    - Key = `[实体指针][成员名]`（如 `obj_abc:name`）
    - Value = 二进制原始数据 **或另一个指针**
    - 每个成员独占一个“格子”，点查 O(1)

> ✨ 比喻：`main` 是一排带双标签的抽屉（“谁的 + 叫什么”），拉开就能拿到内容。

### ▶ 嵌套？靠指针链接！

```json
{
  "user": { "name": "Bob" },
  "tags": ["a", "b"]
}
```

存储时：

- `main[parent_ptr + "user"]` → `child_obj_ptr`（17B 指针）
- `main[parent_ptr + "tags"]` → `tags_set_ptr`（17B 指针）
- 子对象/集合各自在 `set`/`main` 中定义

→ 整棵树被“拍扁”，但可通过指针完整重建。

---

## 四、关键设计原则

|原则|说明|
|---|---|
|**指针化引用**|所有复杂关系通过指针连接，避免冗余复制|
|**二元归一**|仅两种基础结构：**对象**（键值对容器）和 **集合**（无序元素容器）|
|**扁平化存储**|利用 LMDB 的排序与遍历优势，将嵌套转为高效 KV|

---

## 五、一致性如何保障？

LMJCore 在灵活性与安全性之间取得平衡：

- ✅ **允许“缺失值”**：成员已在 `set` 注册，但 `main` 中暂无值 → 合法中间状态（如分步初始化）
- ❌ **禁止“幽灵成员”**：`main` 中有值，但 `set` 中未注册 → 视为**严重数据损坏**
    - 提供审计函数 `lmjcore_audit_object()` 主动检测
    - 正常写事务下**不可能出现**（原子性保证）

> 💡 这种设计让上层既可动态增删字段（无模式），又能在异常时快速发现并修复问题。

---

## 六、为什么这样设计？优势在哪？

|优势|说明|
|---|---|
|**极致读性能**|成员可并发点查 `main`，无需递归解析嵌套|
|**局部更新**|修改一个字段只需更新一个 `main` 格子，不影响父结构|
|**继承 LMDB 优势**|ACID 事务、零拷贝、内存映射、崩溃安全|
|**真正无类型**|Value 是纯二进制，上层可自由编码（JSON、Protobuf、自定义）|
|**无限可扩展**|通过指针轻松构建图、树、双向引用等复杂拓扑|

## 七、集合（Set）的重要说明

LMJCore 中的**集合**对应传统概念中的数组，但有一个关键区别：

### ⚠️ 集合是无序的

```json
// JSON 数组
["banana", "apple"]
```

存储时：
```
set[ptr_set] → "banana"
set[ptr_set] → "apple"
```

由于 LMDB 自动按字典序排序，实际存储为：
```
set[ptr_set] → "apple"
set[ptr_set] → "banana"
```

**这意味着**：
- 集合**不保留插入顺序**
- 集合**自动去重**（同一元素只能出现一次）
- 集合**按字典序自动排序**
- **删除最后一个元素时，该指针在 `set` 中会被 LMDB 自动删除**（集合回到空态）

### ⚠️ 空值语义：空态是默认态

**实体空间预先存在，指针是坐标。** `lmjcore_obj_new()` / `lmjcore_set_new()` 只分配坐标，
不写任何存储。

- `set` 中有 Key = **已实化**（`entity_stat` 返回 1）
- `set` 中无 Key = **空态**（默认态，`entity_stat` 返回 0）

由于 `set` 基于 LMDB 的重复键实现，**长度为 0 的 value 是非法值**（键已存在时写入 0 长度
value 会返回 `MDB_BAD_VALSIZE`；只有键不存在时才被勉强接受，且会被第一个真实 value 静默
覆盖）。因此内核不写「空标记」，而是用 Key 的**有无**表示两种状态：

```
// 添加元素
set[ptr_set] → "apple"
set[ptr_set] → "banana"

// 删除元素
删除 "apple" → set[ptr_set] 仍保留 "banana"
删除 "banana" → LMDB 自动删除该 Key，集合回到空态（坐标依然有效）
```

> **内核语义**：
> - `lmjcore_obj_new()` / `lmjcore_set_new()` **只分配坐标、不写存储**（不需要事务）；
> - 首次写入成员/元素即完成**实化**（写入侧不做状态检查）；
> - 空态坐标调用 `lmjcore_entity_stat()` 返回 **0**。

### 对象的空成员列表行为

**对象同理**，因为对象的成员名列表也存储在 `set` 中：

```
// 对象有两个成员
set[ptr_obj] → "age"
set[ptr_obj] → "name"

// 删除所有成员注册后
删除 "age" → set[ptr_obj] 仍保留 "name"
删除 "name" → LMDB 自动删除该 Key，对象回到空态
```

当对象的所有成员注册都被删除后：
- 坐标**仍然有效**，只是回到空态——`set` 中的 Key 决定状态，这是正式语义，不是错误
- `lmjcore_entity_stat()` 返回 0
- 再次写入成员即重新实化；遍历 `set` 无法发现空态坐标

### 删除成员的安全保证

**关键设计保证**：成员的删除必须遵循"先删值，再删注册"的顺序：

```
// 删除成员 "name" 的正确流程
1. 删除 main[ptr_obj + "name"] → 先删除值
2. 删除 set[ptr_obj] → "name"  → 再删除注册
```

由于：
- ✅ 可以单独删除成员值（保留注册，表示"有成员但值为空"）
- ❌ 不能单独删除成员注册（会导致幽灵成员）
- ✅ **当 `set` 中成员列表为空时，`main` 中必然没有对应的成员值**

> 💡 **这意味着**：删除对象的最后一个成员时，虽然 `set` 中的键被 LMDB 自动删除，但**不会产生幽灵成员问题**。

### 状态与应对策略

由于实体的状态完全由 `set` 中的 Key 决定：

| 场景 | 行为 / 建议方案 |
|------|------------------|
| 坐标刚分配、尚未写入成员/元素 | 空态（默认）；`entity_stat` 返回 0；写入第一个成员/元素即实化 |
| 空态上的读取/统计/删除 | `obj_get`/`set_get` 在结果中记 `ENTITY_NOT_FOUND` 错误位；`stat`/`del` 直接返回 `ENTITY_NOT_FOUND`（无内容可操作） |
| 需要在空态上"占位" | 写入一个占位成员（如 `_empty`）保持已实化 |
| 需要枚举全部坐标 | 在应用层维护独立索引（仅记录指针，不存储结构） |

> ⚠️ **重要限制**：外部索引**无法替代 `set` 的作用**。如果 `set` 中没有定义，即使外部索引记录了指针，也无法解析实体的结构。

### 如果需要有序列表怎么办？

在 Value 中编码顺序信息：

```c
// 格式：[4B 小端序下标][原始值]
set[ptr_set] → "\x00\x00\x00\x00banana"
set[ptr_set] → "\x00\x00\x00\x01apple"
```

读取后按前 4 字节排序即可还原原始顺序。

### 使用场景建议

|场景|推荐结构|
|---|---|
|标签、权限组、集合运算|**集合**（无序，自动去重）|
|时间线、排行榜、队列|**有序列表**（在集合中编码下标）|
|键值对数据|**对象**|

---

## 八、给开发者的建议

- **顺序不是内核的事**：`set` 不保插入序。若需有序数组，请在 Value 中编码下标（如前 4 字节）。
- **成员名 ≤ 493 字节**：受 LMDB Key 长度限制（17B 指针 + 成员名 ≤ 511B）。
- **指针生成需唯一**：内核不校验唯一性，冲突会导致数据覆盖。
- **扩展类型请用成员名**：不要改指针首字节！可通过 `_type` 成员实现应用层类型系统。
- **集合 vs 对象的选择**：
    - 需要键值对 → 用**对象**
    - 只需要元素列表（无键名） → 用**集合**

---

## 九、总结

LMJCore 的本质是：

> **用最简模型（对象 + 集合 + 指针），在 LMDB 之上构建一个高性能、强一致、无模式的存储内核。**

它不做查询，但为查询铺平道路；它不解释类型，但为类型留足空间。  
如果你需要一个**可嵌入、低延迟、高可靠**的底层存储引擎，LMJCore 提供了一个优雅而强大的选择。
